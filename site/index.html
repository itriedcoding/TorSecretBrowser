Private browsing, routed through Tor.

Tor Secret Browser is a small, hardened Electron browser whose only way out to the network is the local Tor daemon it launches and manages for you. Every tab is proxied, DNS is resolved inside Tor, and .onion addresses just work.

What it actually does

No marketing fluff — this is a from-scratch Chromium shell, not a reskinned Tor Browser. Here is precisely how each guarantee is implemented.

All traffic through Tor

Every tab session is forced to socks5://127.0.0.1 with proxyBypassRules: '<-loopback>'. Chromium's SOCKS5 uses remote DNS, so hostnames are resolved by Tor, not by you.

Native .onion support

Onion names are resolved by Tor over the same SOCKS5 channel. Paste any onion address and it loads — no extensions, no extra configuration.

No DNS or WebRTC leaks

The generated torrc sets SafeSocks 1, and the process runs with WebRTC forced to disable_non_proxied_udp. Tor carries no UDP, so WebRTC cannot escape.

Circuit isolation per tab

Each tab gets its own in-memory session and its own local SOCKS5 relay that injects unique credentials, so distinct tabs get distinct Tor circuits.

Privacy by default

No telemetry switches, no persistent profile. Partitions are created without the persist: prefix, so cookies, cache and storage live only in memory for the tab's lifetime.

One-click New Identity

"New Identity" sends SIGNAL NEWNYM to Tor, rotates each tab's SOCKS credentials and drops all per-tab storage, giving you fresh circuits.

Clearnet + onion directory

The new-tab page ships a verified directory of Tor Project and popular clearnet/.onion addresses, each with a copy button, plus a paste-to-open box. The same list lives on the Links page.

How it works

The browser UI and the Tor process are cleanly separated. The renderer only speaks to the main process over a narrow, explicitly-listed IPC bridge.

+---------------------------------------------------------------+
|  Electron main process (Node.js)                              |
|                                                               |
|   index.js  ------------.                                     |
|      |  applies privacy switches, owns windows & IPC         |
|      +-- tor-manager.js  |  spawns + supervises the tor daemon|
|      |      '-- tor-control.js  (Tor control protocol client) |
|      +-- privacy.js      |  proxy rules, leak guards, injected|
|      |                   |  hardening script                  |
|      +-- socks-shim.js   |  per-tab SOCKS5 relay -> Tor creds |
|      +-- paths.js        |  finds the tor binary              |
|      '-- tabs.js         |  one WebContentsView + isolated    |
|                          |  session per tab                  |
|                                                               |
|   IPC (contextBridge)                                         |
|      v chrome-preload.js        v tab-preload.js             |
|   renderer/ (tab strip,      web pages (isolated, sandboxed,  |
|   toolbar, status overlay)    proxied, WebRTC stripped)       |
+---------------------------------------------------------------+
        | (loopback only)         | (loopback only)
        v                         v
  [ SocksShim per tab ] --> [ tor daemon ] --> Tor network (3 hops)
Why the per-tab relay? Chromium rejects credentials embedded in a proxy rule string and silently installs no proxy at all. Each tab therefore points at its own loopback relay, which accepts plain SOCKS5 from Chromium and re-issues the request to Tor with that tab's unique username and password — making per-tab circuit isolation reliable.

Honest limitations

These are real and stated up front. If you need the strongest anonymity guarantees, use the official Tor Browser.

Fingerprint resistance is partial. This build reuses Chromium via Electron. Its fingerprinting surface differs from Firefox/Gecko, and Tor Browser's letterboxing and first-party isolation are not reproduced.
Isolation is per tab, not per site. Tabs are isolated from each other; there is no first-party isolation inside a single tab.
WebRTC is disabled, not proxied. Sites that require WebRTC media will not work. This is deliberate.
No extensions, password manager or sync. Anything that could punch a hole through the proxy is intentionally absent.
